# 全遊戲的效能與卡頓檢查（2026-11-24）

上一次全面的量測是 2026-11-15（`test-results/perf-campaign/mv6-on.md`，docs/perf-campaign-plan.md）。之後加了無邊界地圖（11-22）、機獸（11-19）、敵人的閃避（11-21）、身體部位破壞（11-21～22）、AI 音效的分包（11-23），都還沒量過。這一輪**先只量不修**，報告出來再和使用者決定優化的分期。

使用者的決定（2026-11-24）：平板要量——使用者不在電腦旁，改成在這台模擬平板（解析度、2 倍像素、觸控＋內顯＋CPU 降速），遊戲內的效能紀錄留著之後實機用；第 2、3 周目的委託先不跑；多人先不量。

**全部的項目一律用低標跑**（2026-11-24 使用者定案：要確認一般的設備就跑得順）：內顯 Intel UHD 770＋CPU 降速 1/4，畫面 1600×900（第 4 期另外是平板的解析度）；`perf-all.js --hw` 改回這台的 RTX 4070、不降速（比較用）。第 0 期試跑：低標的 Lattice-9 平均 18.5 fps、40 秒內卡頓 95 次。

**目標**（2026-11-24 使用者定案）：低標的裝置上 fps 至少 24～30——報告的每一項標 ✅（平均 30 以上）／△（24～30）／✗（24 以下），開頭列出不合格的項目。**自動重跑**：每一項跑完檢查結果（沒有檔案、格數太少、出擊沒跑完、頁面錯誤），有問題時關掉殘留的無頭瀏覽器重跑，最多 3 次（主線以 `--resume` 接著跑）。

## 量什麼

- 每一格：主迴圈的耗時、兩格的間隔；平均 fps、p50／p99、最差 1% 的 fps
- 卡頓：兩格間隔 ≥ 50 ms（33～50 ms 是小卡頓），歸因照 perf-campaign 的分類：著色器編譯、GC、事件、主迴圈的哪一段、迴圈外的長任務、迴圈外（顯示卡／瀏覽器）
- 進場：按下出擊到可以操作
- 記憶體：JS heap、three.js 的幾何／貼圖／程式數、場景物件、音效緩衝、DOM（長時間測試每輪先回收記憶體）
- 新系統的計時（`scripts/perf-lib.js` 的 `instrument`）：`wrapTick`（無邊界地圖的搬移與 deepWrap）、`mvTick`（地圖載具）、機體的 `e.updateAI`／`e.move`／`e.dgMove`（閃避）／`e.bodyTick`（身體部位破壞）／`e.specialFx`／`e.mvfxTick`（全部機體合計）、`sfx.b64`／`sfx.needGroup`（AI 音效包的解碼）、事件 `beastSpawn`

## 弱裝置的模擬

`scripts/perf-lib.js` 的 `launch` 讀環境變數：`PERF_GPU=low` 加 `--force_low_power_gpu`（這台會改用內顯，WebGL 的 renderer 字串確認過）、`high` 強制獨立顯示卡；`PERF_TABLET=1180x820` 把每個新的瀏覽器環境改成這個畫面大小、2 倍像素、觸控（`pointer: coarse` 成立，取代各腳本自己的 viewport）；`PERF_CPU=4` 每個新分頁以 DevTools 的 `Emulation.setCPUThrottlingRate` 降速（`newPage` 時等它設定好；長運算量到約 4.3 倍慢）。perf-probe、perf-campaign、perf-hub、cine-perf 都經過它。

## 遊戲內的效能紀錄（之後給平板實機用）

`game/perf-rec.js`：標題「工具與其他」→「效能紀錄」→「開始紀錄」，或網址加 `?perfrec`（從開網頁就開始）。紀錄中左下角顯示 fps 與卡頓次數；停止時從伺服器網址開的會上傳到 `PUT /api/perf/<id>`（`server-models/perf/<id>.json`，紀錄中每分鐘也上傳一次，`GET /api/perf` 列出），直接開檔時「下載 JSON」。沒在紀錄時不包裝任何方法。

內容：裝置（UA、畫面大小、dpr、核心數、WebGL renderer、觸控）、設定（`ctrl`）、每一格的間隔與主迴圈耗時（Uint16、0.1 ms，base64）、情境（state｜主題｜變體｜出擊｜區段｜視角，改變時一筆）、卡頓（≥ 50 ms：那一格與上一格各段的耗時、著色器編譯、GC、前 2 秒的事件、敵人數）、每秒的記憶體（heap、幾何、貼圖、程式、繪製次數、三角形）、長任務。iPad 的 Safari 沒有 `performance.memory` 與長任務，heap 記 0。

- **每一格的大頭**：`renderMain`（其中軟粒子那一次算繪 `pipe.renderSoft` 10～38 ms）、`updateCamera`（遮擋的射線 5～10 ms）、`drawHud`（4～7 ms）；卡頓的歸因 `renderMain` 遠多於 GC。
- **任務中才編譯著色器**：全新的瀏覽器環境一場 80～100 個程式、合計 15～45 秒（內顯上每個更慢；實際玩家第二次起有 `mech_cordon_shader_warm2` 會好一些）。
- **記憶體洩漏**：長時間測試回收記憶體之後 heap 244 → 2583 MB（9 輪）、幾何 540 → 2794、貼圖 191 → 802、程式 45 → 162，fps 跟著掉、卡頓變多；主線連打時頁面到 3 GB 以上，量測本身兩次被系統停掉（之後總控加了 8 GB 的記憶體防護，平板主線的 c3s2 因此只量到 1 段）。
- 量測的瑕疵：`fill-c4s3a-4` 停在模組三選一（0 fps 無效）；`fill-*` 報告上的地圖欄顯示 industrial 是預設值，實際是那個出擊的主題。

## 記憶體洩漏的修正（2026-11-25，`cb3ee7008`）

追查工具：`node scripts/leak-probe.js --rounds=N [--hub] [--snap --census=prop:<屬性>] [--undisp]`（反覆出擊、數實例、找留著舊物件的路徑、記憶體快照依保留路徑統計、離場時沒釋放的幾何），快照分析 `scripts/heap-retain.js`。

- 主因：無邊界地圖的通用掃描把掃過的物件記在 `World._dc.seen`、掃完沒清，經由 Game 上記著舊地圖的欄位掃到上一張 World，每張新地圖都串著上一張，一張都不回收
- 其他：Game 上記著上一張地圖或機體的欄位（`clearMission` 一起清）、`render/detail.js` 以參數當鍵的幾何快取沒有上限（改成換代）、小細節分級只登記不移除、離場的物件只拿出場景沒釋放幾何（three.js 的繪製狀態留著頂點資料）
- 低標的長時間測試（9 輪，`test-results/perf-all/leakfix/`）：回收之後 heap 243 → 970 MB（修改前 244 → 2583 MB）、幾何 540 → 1850（2794）、貼圖 191 → 742（802）。獨立顯示卡 5 張地圖繞兩圈時第二圈持平在約 1 GB
- 每輪的 fps 修改前後差不多（第 8、9 輪的水壩與集散場都在 18～20）：原本報告「fps 跟著掉」其實是那幾張地圖本來就慢，和洩漏無關
